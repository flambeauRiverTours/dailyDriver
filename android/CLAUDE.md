# android/ — CLI Launcher

Registered as the device HOME activity: a single full-screen Compose surface (scrollback transcript + input line) that replaces the home screen and routes input through the T0–T3 command pipeline. Room is the local source of truth for notes, checklists, and aliases. See root [`../CLAUDE.md`](../CLAUDE.md) for project-wide constraints and [`../docs/design.md`](../docs/design.md) §4 for the full design.

Current state: `com.example.dailydriver`, `minSdk`/`targetSdk` pinned to 33, `compileSdk` at 36 (see note below), Compose + Material3. Working end to end and on-device verified: the CLI shell (`shell/`) with a live-filtering, tap-or-Enter-or-auto-launch `:apps` browse view backed by the real app index (`apps/`, wired into `MainActivity` at T012). `settings/SettingsLauncher` is now wired in — `:settings` fires it via T140's dispatcher (T142). Room now exists (T007, `alias/`) — aliases only so far, no notes/checklists schema yet. No MediaPipe dependency yet. T0 now has a real dispatcher (`command/ReservedCommandParser.kt`, T140) — `:apps`, `:settings`, `:note`, `:alias`, and `:notif` are all registered through it; `:note` just records a placeholder until the real editor overlay (T020) exists, `:alias` lists what's currently defined (`alias/AliasListing.kt`), `:notif` (T147, `notifications/`) browses active notifications behind the project's first special-access permission (`NotificationListenerService`, granted by hand under Settings → Notification access — no runtime dialog); `:help` and its bare-`?` shorthand (T145) print a help listing **generated from the registry itself** (`command/HelpText.kt` + `CommandHelp` on each `RegisteredCommand`), so a newly registered command documents itself. **Every reserved command in the design doc now exists.** T1 (T008) is live — fuzzy app matching previews and auto-launches on Enter/pause. T009's whitespace-based T2/T3 escalation classification (`command/EscalationTier.kt`) now feeds T010's real fallback (`command/UnmatchedResponse.kt`): unmatched input gets a one-line pointer to `:help` rather than a placeholder, and prose degrades there too while the SLM is absent. **T2 is the only tier still missing** (T036). T146 added the status row above the transcript (`shell/StatusLine.kt` + pure `StatusLineFormat.kt`) — time left, date right, colon blinking at 1 Hz, ticking only while RESUMED; T148 put an unread-notification dot at its leading edge. T149 made the app immersive (both system bars hidden, transient-on-swipe) — **note this is re-applied in `MainActivity.onWindowFocusChanged`, not just `onCreate`**, because the system restores the bars on every focus loss.

**The unit suite is 410 tests** (T150 swept it from 187, and fixed two latent bugs it turned up — a case-sensitive alias sort and a blank-title notification row). Several files now carry registry-wide *property* tests rather than only per-case ones: adding a reserved command is automatically checked for duplicate tokens, dispatchability, auto-space, and being documented in `:help`. Keep that style when adding commands — the per-case test is the easy half.

**Lint baseline is 0 errors / 10 warnings** (7 `GradleDependency`, 1 each `RedundantLabel`, `OldTargetApi`, `AndroidGradlePluginVersion`) — it moved from 9 at T146 when `lifecycle-runtime-compose` was added. The lifecycle version ref is pinned at 2.10.0 on purpose: 2.11.0 needs `compileSdk 37` **and** AGP 9.1.0, so its stale-version warnings aren't actionable without an AGP major upgrade.

**Running Gradle from the command line just works** — no `JAVA_HOME=` override needed. The system-wide `JAVA_HOME` on this machine points at JDK 11, which AGP 8.10 rejects (requires 17+), but `~/.gradle/gradle.properties` (machine-local, outside this repo, not something a fresh clone gets) pins `org.gradle.java.home` to Android Studio's bundled JBR. If a fresh environment hits "Android Gradle plugin requires Java 17," that's this setting missing, not a project problem — same fix, or point `JAVA_HOME` at a real JDK 17+.

## Target device

**Samsung Galaxy S20 FE 5G, model SM-G781V — Snapdragon 865 — Android 13 (API 33).** Pinned at T001; every latency/memory/battery benchmark in the project cites this device. `minSdk`/`targetSdk` are set to 33 to match it exactly — no broader compatibility is a project goal, so there's no reason to target a wider runtime range.

`compileSdk` is 36, not 33 — it's a build-time-only setting (which API surface the compiler sees), independent of the runtime `minSdk`/`targetSdk` above. Already-present AndroidX dependencies (`core-ktx` among them) hard-require `compileSdk 36`; keep it at whatever the newest dependency needs, and don't conflate it with the device-pinning decision when adding future dependencies.

SM-G781V is the Verizon 5G variant, which ships with Snapdragon 865 — relevant once GPU-backend LoRA work starts (T037), since the Exynos 990 variant of this phone (the international 4G-only SM-G780F) is a different chipset with different GPU/LoRA behavior.

## Testing — TDD is the default workflow

Write the test before the implementation for anything with logic in it. This module has more test-shaped surface than most Android apps — tier resolution, JSON repair, Room queries, and merge/tag parsing are all pure-ish functions with clear inputs and outputs, which is exactly where TDD pays for itself.

- **Red, green, refactor.** For new pipeline logic, DAOs, parsers, or ViewModels: write a failing unit test first, make it pass with the minimum code, then clean up. Don't write the implementation and backfill tests afterward — if a task shows up without tests in the same commit, treat that as unfinished, not done.
- **Keep pure logic Android-independent** so it lives in `src/test/` (fast, JVM-only JUnit) instead of `src/androidTest/` (slow, needs a device/emulator). T1 fuzzy matching, T2's JSON extraction/repair/validation chain, tag/hashtag parsing, and alias resolution should all be plain Kotlin with no `android.*` imports, tested with local JUnit.
- **Cover the edge cases the design doc calls out as risky**, not just the happy path: empty/whitespace-only input, malformed JSON (trailing commas, unquoted keys, markdown fences) at every stage of the T2 repair pass, low-confidence and `unknown`-intent outputs that must drop to T3, and T0/T1 boundary cases (ties, near-threshold fuzzy scores).
- **Room DAOs get instrumented or in-memory-database tests before the schema is treated as stable — when the DAO itself carries real logic to get wrong.** The outbox (T018+) is the clear case: a mutation whose transactional write isn't covered by a test isn't trusted. A DAO that's just a `SELECT *` and a plain `@Insert`, with every actual decision (conflict detection, parsing, cycle checks) living in already-tested pure functions elsewhere — `AliasDao`, T007, is the precedent — doesn't need its own instrumented test just to exercise Room's own codegen. Judge by how much logic the DAO itself carries, not by "it's a DAO." Note that "Room's codegen is well-tested" is not the same as "your use of it is obvious": conflict strategies, foreign keys and transaction boundaries interact in ways that look fine and aren't (see the `@Upsert` note under Room patterns).
- **⚠️ Actually RUN the instrumented tests before committing, whenever existing ones cover what you changed** — today that means anything touching the database (`NoteDaoTest`), and any Compose UI tests as they get written. Writing a test is not the same as running it, and "it compiles" proves nothing about SQLite semantics. (This is about *running* suites that exist; the priority of *writing* new UI tests is the separate question two bullets down.)

  ```bash
  ./gradlew :app:connectedDebugAndroidTest
  ```

  **This is not optional caution — it is the only thing that has ever caught a bug in this layer.** T018 shipped a note upsert that silently cascade-deleted its own pending outbox row on every save. The unit suite (410 tests), lint, and the Kotlin compiler all passed it; a single instrumented test failed on the first run. Anything that only manifests against real SQLite is invisible to everything else we run.

  Operational notes, each learned the hard way at T018:
  - **`adb` is not on PATH, and doesn't need to be** — Gradle resolves it from `sdk.dir` in `local.properties`. Only a booted device is required, so don't conclude these can't be run.
  - **An emulator is fine here.** Database, transaction and SQL semantics aren't device-specific; a local AVD is faster and more repeatable than the S20 FE. Save the physical device for what genuinely needs it — permissions, window insets, notifications, IME behavior.
  - **A stale KSP cache survives `clean`.** If a build fails with `Storage for [...id-to-file.tab] is already registered`, run `./gradlew --stop` — the bad state is in the daemon, not on disk.
  - A phantom `offline` emulator in `adb devices` will fail the run with "No online devices found" even when a working device is attached; `adb kill-server` clears it.
- **The shared fixture corpus is the contract, not an afterthought** (T070–T072). Sync/merge logic is TDD by construction here: the JSON corpus (`base`/`local`/`remote`/`expected`) is written before the Kotlin implementation that must satisfy it, and the same corpus drives the C# xUnit suite. If Kotlin and C# disagree, that's a failing test, not a judgment call.
- **Compose UI tests** (`androidx-ui-test-junit4`, already in the scaffold) cover the critical interaction paths — editor overlay open/dismiss, checklist check/reorder, keyboard shortcuts — using semantics/test tags rather than brittle text matching. UI tests are lower priority than the logic tests above; don't let them block on the emulator becoming available.
- No test dependencies beyond what's already in `libs.versions.toml` (JUnit4, AndroidX Test, Espresso, Compose UI test) are assumed. Adding a framework (Robolectric, Turbine, MockK, etc.) is a deliberate one-line addition to the version catalog, not an incidental import.

## Note editor (`editor/`, T020/T021)

Opened by `:note` (bare) or `:note <name>` (pre-fills the title); opening an *existing* note by name is T025. Rendered inline in `ShellScreen` as a **layout swap, not a floating `Box`** — it takes the prompt's place and grows upward from the bottom as you write, capped at 420dp, which is what lets one surface serve both quick capture and long-form journalling.

- **`NoteDraft` is the pure half** — blank-vs-content, the blank-title stamp, conversion to a `Note` row. Keep logic there rather than in the ViewModel; it's the only part that can be unit-tested.
- **Nothing is persisted until there's content**, so an accidental `:note` leaves no row. `NoteDraft.persisted` is what tells discard the difference between "forget this" and "soft-delete a real note".
- **A blank title becomes a `Wed 19 Aug - 14:32` stamp derived from `createdAt`, never `now()`** — otherwise the title drifts on every autosave, and an entry written past midnight would change date mid-write.
- **✓ keeps, ✗ discards** (soft delete). **✗ no longer confirms** — T138 landed and the confirmation went with it, as that bullet always said it should. Discarding a note with content soft-deletes it and offers an inline undo row; an empty draft is dropped silently.
- **Undo is one action deep, not a stack** (T138, `editor/UndoableAction.kt`). It covers discarding a note, deleting a checklist row, and note↔checklist conversion. The offer survives the editor closing, because discarding closes it — `ShellScreen` renders `editor.pendingUndo` whether or not a draft is open. Restoring a discarded note works by re-saving the draft, which un-tombstones the row; that claim is pinned by instrumented tests rather than assumed, since it is the same `@Upsert` behaviour that bit T018.
- **Tag chips are a view over the body's hashtags** (T139, `notes/TagEditing.kt`). Adding or removing a chip edits `#tags` in the body text; nothing writes `note_tags` directly, so `NoteDao`'s derive-on-save remains the only writer. The task list originally suggested unioning chip-set and body-set — don't: that is two writers of one fact.
- **BACK keeps rather than discards.** It's ambiguous, and autosave has already written the text.
- **`:notes [query]` browses and searches** (T025/T026, `shell/NoteListView.kt`); `:note` still writes one, and `:note <name>` opens-or-creates. Rows are two lines — title plus body snippet — because blank titles default to a timestamp and a list of those is unidentifiable. Opening an existing note expands the editor to full height.
- **⚠️ Auto-space only applies to `autoSpaceableTokens`, not every token.** `:note`/`:notes` is a prefix pair: auto-spacing `:note` on completion made `:notes` untypeable (the `s` landed after the inserted space). Any future token that is a prefix of another inherits this — the rule is enforced in `ReservedCommandParser` and pinned by a test, so don't reintroduce `reservedCommandTokens` at that call site.

## Kotlin/Compose conventions

- **One Activity.** The launcher, the editor, and every overlay live in the same Activity as Compose surfaces — no `startActivity`, no navigation library, no extra Recents entries. The editor (§4.6 of the design doc) is a Compose overlay composited over the launcher, not a separate screen.
- **State hoisting.** Composables stay stateless where practical; state lives in a ViewModel (`androidx.lifecycle.viewmodel.compose`) or the Room-backed repository layer beneath it, not in the composable itself.
- **Dark-only theme.** `ui/theme/` defines one palette. Do not add a light theme or a theme toggle — this is a deliberate asymmetry with the desktop client (design doc §5.3).
- **Package namespace.** Still the Android Studio default (`com.example.dailydriver`). Rename deliberately in one commit if/when a real namespace is chosen — don't let it drift piecemeal across files.

## T0–T3 command pipeline

The command pipeline is the core of the app. **The SLM (T2) is never the front door** — see the root hard constraints.

| Tier | Handler | Latency budget | Handles |
|---|---|---|---|
| T0 | Exact match — reserved commands (`:apps`, `:settings`, `:note`, `:alias`, `:help`/`?`) and user aliases | < 5 ms | Muscle-memory input |
| T1 | Fuzzy match over the `PackageManager` app index (normalized edit distance + prefix/acronym boost) | < 50 ms | `chr` → Chrome |
| T2 | SLM intent + slot extraction (MediaPipe) | ~1 s | Free-form natural language |
| T3 | Fallback — app-name search, else help | — | Everything else |

- Escalate T0 → T1 → T2 only when the prior tier's confidence is below threshold; T1 short-circuits on a single high-confidence match.
- Input containing whitespace with no T0/T1 hit goes straight to T2 — multi-word input is almost always prose, don't waste a tier on it.
- **Log every T0/T1 resolution** as `(raw_input, resolved_intent)` locally (T014). This is the fine-tuning dataset's real-usage seed — treat it as load-bearing, not telemetry.
- T3 is what makes T2 shippable: the SLM is allowed to fail, the launcher is not.

## Room patterns

- **Outbox from day one** (T018, built). Every mutation to **synced** data — notes, and the checklists derived from them — writes an outbox row in the same transaction as the entity change; that pairing is what makes sync resumable after an interrupted push. Don't add a synced table that can be mutated outside a transaction that also touches the outbox. **Aliases are explicitly excluded** (corrected 2026-08-19): this bullet used to say "notes/checklists/aliases", which predated T097 resolving alias sync as "no". An outbox row for an alias would never drain, because nothing pushes it.
  - `NoteDao` enforces this structurally rather than by convention: the raw insert/tag/enqueue operations are `protected`, so callers can only reach `@Transaction` methods that already do the right thing. `upsertLocal`/`markDeletedLocal` enqueue; `applyRemote` deliberately doesn't (pulled state is already the server's).
  - **The outbox coalesces** — one row per dirty note, keyed by `noteId`, not one per mutation. §4.6's debounced autosave would otherwise queue hundreds of rows pushing identical state. Consequences worth knowing: `enqueue` uses `IGNORE` so `baseRev` stays pinned to when the note *first* went dirty (that's the conflict comparison point, §7.2), and `confirmPushed` only drains the row if the note hasn't changed mid-push.
- **Markdown is the stored format**, per the root constraint — not a rich-text model. Checklist items are `- [ ]` / `- [x]` lines parsed into structured items for the UI, not stored as separate normalized rows (that parser lands with T023/T024). Hashtags (`#work`) are parsed out of the body on save and indexed for querying; the body stays the single source of truth. **Tags live in a `note_tags` join table**, not a delimited column — exact matching, because `LIKE '%work%'` also matches `#workout`.
- **Tag parsing is a cross-language contract, not local logic** (`notes/TagParsing.kt`, T019). Design doc §7.3 has `Notes.Shared` implementing the same rules in C# and names this "the seam where bugs will live", so the rules are pinned in **`fixtures/tag-parsing.json`** at the repo root and executed by both suites. **Change the fixture and both implementations — never one alone.** The repo-root `fixtures/` dir is on the unit-test classpath via a `sourceSets` entry in `app/build.gradle.kts`.
  - `NoteDao.upsertLocal` **derives** tags from the body rather than accepting them, so a caller can't supply a set that disagrees with it. `applyRemote` still takes them, because those are the server's — that asymmetry is deliberate and matters if tag assignment ever moves server-side.
- **One database, `dailydriver.db`** (`data/DailyDriverDatabase.kt`), built once via `DatabaseProvider`. Notes and the outbox *must* share it — a transaction can't span two SQLite files. Never call `Room.databaseBuilder` for it a second time. **`exportSchema` is off, and that's a known gap (T151)** — enabling it on Room 2.8.4 here exports once and then fails every subsequent build with an `AbstractMethodError` in kotlinx-serialization. Solve that before the first real migration; don't just flip the flag.
  - **Notes use `@Upsert`, never `@Insert(onConflict = REPLACE)`.** SQLite implements REPLACE as delete-then-insert, and both `outbox` and `note_tags` CASCADE off `notes` — so a REPLACE on a note silently deletes its pending outbox row. This shipped as a real bug at T018 and was caught only by the instrumented tests. Same trap applies to any future table with children.
- **Aliases are device-local and not synced** (open item T097, currently resolved as "no"). Don't add an alias sync path without revisiting that decision first.
- Room is authoritative; the network is an optimization. No UI read or write should ever await a network call — that's the desktop client's rule too (design doc §5.4), and Android follows the same shape even though it isn't stated as an explicit constraint there.

## MediaPipe (T2) — GPU backend + LoRA constraints

- **Runtime:** MediaPipe LLM Inference API (`LlmInference` / `LlmInferenceOptions`). All inference sits behind an `InferenceEngine` interface (`suspend fun infer(prompt: String): String` + lifecycle) — `MediaPipeEngine` is the only implementation for now, but the interface exists so `LiteRtLmEngine` can be swapped in later (MediaPipe is in maintenance-only mode upstream; see design doc §4.4).
- **LoRA requires `backend = "gpu"`.** It is not available on CPU backend, applies to attention layers only, and MediaPipe documents it as experimental. Do not attempt LoRA on the CPU backend.
- **Model choice is gated on LoRA support**, not picked upfront: candidates are Gemma-2 2B (LoRA explicitly documented) and Gemma-3 1B 4-bit (smaller/faster, LoRA support undocumented). T037 is a timeboxed GO/NO-GO spike on the target device before committing — don't build downstream fine-tuning work against a model that hasn't cleared that gate.
- LoRA adapters are trained with PEFT (`target_modules = ["q_proj","v_proj","k_proj","o_proj"]`) and converted with MediaPipe's `converter.ConversionConfig()`.
- **No grammar-constrained decoding** in MediaPipe (unlike llama.cpp's GBNF). Schema adherence for the intent/slot JSON output is defended in layers, in order: tight few-shot prompt with the schema inline → low temperature (~0.1) → extract the first balanced `{...}` span → repair pass (trailing commas, unquoted keys, markdown fences) → validate against schema, drop to T3 on failure or low confidence. Don't skip layers to simplify — each one is there because the previous one alone was measured as insufficient.
- Model weights are downloaded at first run (WorkManager, SHA-256 verified, unmetered network only) from Blob Storage — never bundled in the APK. The LoRA adapter (single-digit MB) may be bundled. The launcher must be fully functional at T0/T1/T3 before the model exists on-device.
