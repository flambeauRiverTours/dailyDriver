# android/ — CLI Launcher

Registered as the device HOME activity: a single full-screen Compose surface (scrollback transcript + input line) that replaces the home screen and routes input through the T0–T3 command pipeline. Room is the local source of truth for notes, checklists, and aliases. See root [`../CLAUDE.md`](../CLAUDE.md) for project-wide constraints and [`../docs/design.md`](../docs/design.md) §4 for the full design.

Current state: `com.flambeauriver.dailydriver`, `minSdk`/`targetSdk` pinned to 33, `compileSdk` at 36 (see note below), Compose + Material3. Working end to end and on-device verified: the CLI shell (`shell/`) with a live-filtering, tap-or-Enter-or-auto-launch `:apps` browse view backed by the real app index (`apps/`, wired into `MainActivity` at T012). `shell/IntentLauncher` is now wired in — `:settings` fires it via T140's dispatcher (T142). Room now exists (T007, `alias/`) — aliases only so far, no notes/checklists schema yet. **MediaPipe is now a dependency** (T029, `tasks-genai:0.10.35`) and `slm/MediaPipeEngine.kt` is built against it, but **nothing constructs it** — `NoInferenceEngine` is still what runs, and wiring T2 in is T036's job after T037's gate. T0 now has a real dispatcher (`command/ReservedCommandParser.kt`, T140) — `:apps`, `:settings`, `:note`, `:alias`, and `:notif` are all registered through it; `:note` just records a placeholder until the real editor overlay (T020) exists, `:alias` lists what's currently defined (`alias/AliasListing.kt`), `:notif` (T147, `notifications/`) browses active notifications behind the project's first special-access permission (`NotificationListenerService`, granted by hand under Settings → Notification access — no runtime dialog); `:help` and its bare-`?` shorthand (T145) print a help listing **generated from the registry itself** (`command/HelpText.kt` + `CommandHelp` on each `RegisteredCommand`), so a newly registered command documents itself. **Every reserved command in the design doc now exists.** T1 (T008) is live — fuzzy app matching previews and auto-launches on Enter/pause. T009's whitespace-based T2/T3 escalation classification (`command/EscalationTier.kt`) now feeds T010's real fallback (`command/UnmatchedResponse.kt`): unmatched input gets a one-line pointer to `:help` rather than a placeholder, and prose degrades there too while the SLM is absent. **T2 is the only tier still missing** (T036). T146 added the status row above the transcript (`shell/StatusLine.kt` + pure `StatusLineFormat.kt`) — colon blinking at 1 Hz, ticking only while RESUMED; T161 added battery and T171 regrouped it to `[dot] time · date` left, battery right, **with a `·` separator that is load-bearing** — the blinking colon means the time alternates between `4:28` and `4 28`, so adjacency alone left the two fields divided by a gap the same width as the one inside the time; T148 put an unread-notification dot at its leading edge. T149 made the app immersive (both system bars hidden, transient-on-swipe) — **note this is re-applied in `MainActivity.onWindowFocusChanged`, not just `onCreate`**, because the system restores the bars on every focus loss.

**The unit suite is 806 tests** (T150 swept it from 187, and fixed two latent bugs it turned up — a case-sensitive alias sort and a blank-title notification row). Several files now carry registry-wide *property* tests rather than only per-case ones: adding a reserved command is automatically checked for duplicate tokens, dispatchability, auto-space, and being documented in `:help`. Keep that style when adding commands — the per-case test is the easy half.

**Lint baseline is 0 errors / 14 warnings** (11 `GradleDependency`, 1 each `RedundantLabel`, `OldTargetApi`, `AndroidGradlePluginVersion`) — it moved from 9 at T146 when `lifecycle-runtime-compose` was added, and from 10 at T029. **Only one of those four new warnings came from T029's change**: the other three are `GradleDependency` hits on pre-existing refs that appeared because AndroidX published new versions (room 2.8.5, core-ktx 1.19.0, appcompat 1.8.0, activity-compose 1.13.0). `tasks-genai` is *not* among them, which is how we know 0.10.35 is current. T029's own warning was `ChromeOsAbiSupport`, suppressed inline in `build.gradle.kts` with its reasoning beside it. The lifecycle version ref is pinned at 2.10.0 on purpose: 2.11.0 needs `compileSdk 37` **and** AGP 9.1.0, so its stale-version warnings aren't actionable without an AGP major upgrade.

**⚠️ `gradlew` needs two things right for Linux CI, and both were wrong.**

*Line endings.* The repo's `.gitattributes` sets `* text=auto eol=crlf` (Windows-only project), and the exemption for the wrapper was written as `/gradlew`, which anchors to the repo root — but the wrapper is at `android/gradlew`, so it matched nothing. The blanket rule applied, and `eol=crlf` forces CRLF on *every* platform, not just Windows, so Linux CI checked out a shebang reading `#!/usr/bin/env sh
` and every job died with `/usr/bin/env: 'sh
': No such file or directory` (exit 127). The patterns are now unanchored so they match at any depth. Check with `git check-attr text eol -- android/gradlew`.

*The executable bit.* This machine has `core.filemode=false` (the Windows default), so git does not notice or record the executable bit, and `android/gradlew` was committed as 100644. Linux CI runners then check out a non-executable script and every job dies with `./gradlew: Permission denied` and exit 126. Fixed with `git update-index --chmod=+x android/gradlew`. **This can come back**: `./gradlew wrapper --gradle-version=X` rewrites the file, and on Windows it will be re-added without the bit. Check with `git ls-files -s android/gradlew` after any wrapper upgrade. Deliberately *not* patched over with a `chmod` step in CI — that would keep CI green while anyone cloning on Linux or macOS still got a broken wrapper.

**Running Gradle from the command line just works** — no `JAVA_HOME=` override needed. The system-wide `JAVA_HOME` on this machine points at JDK 11, which AGP 8.10 rejects (requires 17+), but `~/.gradle/gradle.properties` (machine-local, outside this repo, not something a fresh clone gets) pins `org.gradle.java.home` to Android Studio's bundled JBR. If a fresh environment hits "Android Gradle plugin requires Java 17," that's this setting missing, not a project problem — same fix, or point `JAVA_HOME` at a real JDK 17+.

## Target device

**Samsung Galaxy S20 FE 5G, model SM-G781V — Snapdragon 865 — Android 13 (API 33).** Pinned at T001; every latency/memory/battery benchmark in the project cites this device. `minSdk`/`targetSdk` are set to 33 to match it exactly — no broader compatibility is a project goal, so there's no reason to target a wider runtime range.

`compileSdk` is 36, not 33 — it's a build-time-only setting (which API surface the compiler sees), independent of the runtime `minSdk`/`targetSdk` above. Already-present AndroidX dependencies (`core-ktx` among them) hard-require `compileSdk 36`; keep it at whatever the newest dependency needs, and don't conflate it with the device-pinning decision when adding future dependencies.

SM-G781V is the Verizon 5G variant, which ships with Snapdragon 865 — relevant once GPU-backend LoRA work starts (T037), since the Exynos 990 variant of this phone (the international 4G-only SM-G780F) is a different chipset with different GPU/LoRA behavior.

## Testing — TDD is the default workflow

Write the test before the implementation for anything with logic in it. This module has more test-shaped surface than most Android apps — tier resolution, JSON repair, Room queries, and merge/tag parsing are all pure-ish functions with clear inputs and outputs, which is exactly where TDD pays for itself.

- **Red, green, refactor.** For new pipeline logic, DAOs, parsers, or ViewModels: write a failing unit test first, make it pass with the minimum code, then clean up. Don't write the implementation and backfill tests afterward — if a task shows up without tests in the same commit, treat that as unfinished, not done.
- **Keep pure logic Android-independent** so it lives in `src/test/` (fast, JVM-only JUnit) instead of `src/androidTest/` (slow, needs a device/emulator). T1 fuzzy matching, T2's JSON extraction/repair/validation chain, tag/hashtag parsing, and alias resolution should all be plain Kotlin with no `android.*` imports, tested with local JUnit.
- **Cover the edge cases the design doc calls out as risky**, not just the happy path: empty/whitespace-only input, malformed JSON (trailing commas, unquoted keys, markdown fences) at every stage of the T2 repair pass, low-confidence and `unknown`-intent outputs that must drop to T3, and T0/T1 boundary cases (ties, near-threshold fuzzy scores).
- **Room DAOs get instrumented or in-memory-database tests before the schema is treated as stable — when the DAO itself carries real logic to get wrong.** The outbox (T018+) is the clear case: a mutation whose transactional write isn't covered by a test isn't trusted. A DAO that's just a `SELECT *` and a plain `@Insert`, with every actual decision (conflict detection, parsing, cycle checks) living in already-tested pure functions elsewhere — `AliasDao`, T007, is the precedent — doesn't need its own instrumented test just to exercise Room's own codegen. Judge by how much logic the DAO itself carries, not by "it's a DAO." Note that "Room's codegen is well-tested" is not the same as "your use of it is obvious": conflict strategies, foreign keys and transaction boundaries interact in ways that look fine and aren't (see the `@Upsert` note under Room patterns).
- **⚠️ Actually RUN the instrumented tests before committing, whenever existing ones cover what you changed** — today that means anything touching the database (`NoteDaoTest`), and any Compose UI tests as they get written. Writing a test is not the same as running it, and "it compiles" proves nothing about SQLite semantics. (This is about *running* suites that exist; the priority of *writing* new UI tests is the separate question two bullets down.)

  ```bash
  ./gradlew :app:connectedDebugAndroidTest
  ```

  **This is not optional caution — it is the only thing that has ever caught a bug in this layer.** T018 shipped a note upsert that silently cascade-deleted its own pending outbox row on every save. The unit suite (410 tests), lint, and the Kotlin compiler all passed it; a single instrumented test failed on the first run. Anything that only manifests against real SQLite is invisible to everything else we run.

  Operational notes, each learned the hard way at T018:
  - **`adb` is not on PATH, and doesn't need to be** — Gradle resolves it from `sdk.dir` in `local.properties`. Only a booted device is required, so don't conclude these can't be run.
  - **An emulator is fine here.** Database, transaction and SQL semantics aren't device-specific; a local AVD is faster and more repeatable than the S20 FE. Save the physical device for what genuinely needs it — permissions, window insets, notifications, IME behavior.
  - **A stale KSP cache survives `clean`.** If a build fails with `Storage for [...id-to-file.tab] is already registered`, run `./gradlew --stop` — the bad state is in the daemon, not on disk.
  - A phantom `offline` emulator in `adb devices` will fail the run with "No online devices found" even when a working device is attached; `adb kill-server` clears it.
- **The shared fixture corpus is the contract, not an afterthought** (T070–T072). Sync/merge logic is TDD by construction here: the JSON corpus (`base`/`local`/`remote`/`expected`) is written before the Kotlin implementation that must satisfy it, and the same corpus drives the C# xUnit suite. If Kotlin and C# disagree, that's a failing test, not a judgment call.
- **Compose UI tests** (`androidx-ui-test-junit4`, already in the scaffold) cover the critical interaction paths — editor overlay open/dismiss, checklist check/reorder, keyboard shortcuts — using semantics/test tags rather than brittle text matching. UI tests are lower priority than the logic tests above; don't let them block on the emulator becoming available.
- No test dependencies beyond what's already in `libs.versions.toml` (JUnit4, AndroidX Test, Espresso, Compose UI test) are assumed. Adding a framework (Robolectric, Turbine, MockK, etc.) is a deliberate one-line addition to the version catalog, not an incidental import.

## Note editor (`editor/`, T020/T021)

Opened by `:note` (bare) or `:note <name>` (pre-fills the title); opening an *existing* note by name is T025. Rendered inline in `ShellScreen` as a **layout swap, not a floating `Box`** — it takes the prompt's place and grows upward from the bottom as you write, capped at 420dp, which is what lets one surface serve both quick capture and long-form journalling.

- **`NoteDraft` is the pure half** — blank-vs-content, the blank-title stamp, conversion to a `Note` row. Keep logic there rather than in the ViewModel; it's the only part that can be unit-tested.
- **Nothing is persisted until there's content**, so an accidental `:note` leaves no row. `NoteDraft.persisted` is what tells discard the difference between "forget this" and "soft-delete a real note".
- **A blank title becomes a `Wed 19 Aug - 14:32` stamp derived from `createdAt`, never `now()`** — otherwise the title drifts on every autosave, and an entry written past midnight would change date mid-write.
- **✓ keeps, ✗ discards** (soft delete). **✗ no longer confirms** — T138 landed and the confirmation went with it, as that bullet always said it should. Discarding a note with content soft-deletes it and offers an inline undo row; an empty draft is dropped silently.
- **Undo is one action deep, not a stack** (T138, `editor/UndoableAction.kt`). It covers discarding a note, deleting a checklist row, and note↔checklist conversion. The offer survives the editor closing, because discarding closes it — `ShellScreen` renders `editor.pendingUndo` whether or not a draft is open. Restoring a discarded note works by re-saving the draft, which un-tombstones the row; that claim is pinned by instrumented tests rather than assumed, since it is the same `@Upsert` behaviour that bit T018.
- **Tag chips are a view over the body's hashtags** (T139, `notes/TagEditing.kt`). Adding or removing a chip edits `#tags` in the body text; nothing writes `note_tags` directly, so `NoteDao`'s derive-on-save remains the only writer. The task list originally suggested unioning chip-set and body-set — don't: that is two writers of one fact.
  - **⚠️ A checklist body has no text field, and that broke tagging** (T169). `parseChecklist` reads any non-blank line as an item, so the `#work` a chip appends became a checkbox you could tick. Fixed by `notes/TagLines.kt` — `splitTagLines`/`rejoin` lift tag lines off before parsing and put them back after, applied at **all four** places the editor reads the body. **Don't fix this in `parseChecklist`**: it is pinned by `fixtures/checklist-parsing.json` and owes a C# implementation, and — worse — `editItems` is `render(transform(parse(body)))`, so a line the parser drops is a line the render deletes. Dropping tag lines there would destroy the first tag you added.
  - **`+ tag` behaves differently in the two modes, and has to.** On prose it appends a bare `#` and returns the cursor to the body (T139's gesture). On a checklist there is no body field, so that `#` landed as a checkbox and typing into it made `- [ ] #shopping` — an item shaped like a tag that can never become one. Checklist mode opens a transient one-line input instead. **That is not a second writer**: it commits through the same `withTag`, and the body stays the only place tags live.
- **BACK keeps rather than discards.** It's ambiguous, and autosave has already written the text.
- **`:notes [query]` browses and searches** (T025/T026, `shell/NoteListView.kt`); `:note` still writes one, and `:note <name>` opens-or-creates. Rows are two lines — title plus body snippet — because blank titles default to a timestamp and a list of those is unidentifiable. Opening an existing note expands the editor to full height.
- - **Every browse view is built from `shell/BottomAnchoredList.kt`** (T176). Pass rows in **natural order** — the component reverses the *layout*, not the data, so reversing before calling cancels out. That mistake is the entire reason it exists: `:apps` opened on Z (T170), `:notes` on the oldest notes and `:tasks` on the least urgent (T175), because each view hand-rolled the same thing and three got it wrong.
- **⚠️ `Arrangement.Bottom` only arranges *slack*** (T170). `AppListView` documented itself as bottom-anchored from T012 and wasn't: it reversed the list by hand and relied on the arrangement to push it down, which does nothing once content exceeds the viewport — so `:apps` opened on `z, y, x, w`. A *filtered* result still sat correctly at the bottom, which is why it survived so long. The fix is `reverseLayout = true` over the A→Z list, which makes item 0 the bottom item and the resting position, rather than an initial `scrollToItem` correcting it a frame later. The fast-scroll rail reverses its **letters** while its **indices** stay A→Z; reversing both sends every letter to the wrong end.
- **⚠️ Auto-space only applies to `autoSpaceableTokens`, not every token.** `:note`/`:notes` is a prefix pair: auto-spacing `:note` on completion made `:notes` untypeable (the `s` landed after the inserted space). Any future token that is a prefix of another inherits this — the rule is enforced in `ReservedCommandParser` and pinned by a test, so don't reintroduce `reservedCommandTokens` at that call site.

## Kotlin/Compose conventions

- **One Activity.** The launcher, the editor, and every overlay live in the same Activity as Compose surfaces — no `startActivity`, no navigation library, no extra Recents entries. The editor (§4.6 of the design doc) is a Compose overlay composited over the launcher, not a separate screen.
- **State hoisting.** Composables stay stateless where practical; state lives in a ViewModel (`androidx.lifecycle.viewmodel.compose`) or the Room-backed repository layer beneath it, not in the composable itself.
- **Dark-only theme.** `ui/theme/` defines one palette. Do not add a light theme or a theme toggle — this is a deliberate asymmetry with the desktop client (design doc §5.3).
- **Package namespace** is `com.flambeauriver.dailydriver`, renamed off the Android Studio default `com.example.dailydriver` at T160. **If it ever changes again, the Room schema directory moves with it**: `app/schemas/` is named by the database class's fully-qualified name, so a rename relocates every exported schema and, if missed, breaks `SchemaExportTest` and all migration tests.

## T0–T3 command pipeline

The command pipeline is the core of the app. **The SLM (T2) is never the front door** — see the root hard constraints.

**⚠️ The tiers are stages of one pass, not separate lookups** (T182–T184, [ADR-0010](../docs/adr/0010-unified-candidate-matching.md)). `command/CommandCandidate.kt` builds **one list** — every app, every alias, every reserved command — and `rankCandidates` runs the stages over the whole of it. Don't add a fourth collection with its own matcher; add a `Candidate`.

| Stage | Handler | Latency budget | Handles |
|---|---|---|---|
| T0 | Exact match over the candidate list | < 5 ms | Muscle-memory input |
| T1 | Fuzzy match over the same list — the seven-strategy ladder in `apps/AppMatching.kt` | < 50 ms | `chr` → Chrome |
| T2 | SLM intent + slot extraction (MediaPipe) | ~1 s | Free-form natural language |
| T3 | Fallback — help | — | Everything else |

- **Ranking is band, then usage, then coverage, then label.** The stage decides the band; within a band the thing you run most wins (`command_usage`, T183). A heavily-used weak match never outranks an unused strong one — that guard is what `CommandCandidateTest` pins hardest.
- **T0-before-T1 is structural now.** An alias named `cam` beats a fuzzy match on Camera because the exact pass completes first, not because anything checks aliases before apps. Don't reintroduce an ordering branch to "make sure" of it.
- **Reserved tokens are fuzzy-matchable** — `:aps` reaches `:apps`. Two consequences. `resolutionOf` must read the same ranking dispatch does: it briefly didn't, and logged `:aps` as a T3 *miss* while the command ran fine. And **a typing pause must not commit a command candidate**, or pausing mid-`:notes` opens the editor on `:note` — that rule lives in `ShellUiState.pauseTarget`.
- **⚠️ Registry casing variants dedupe.** `:tasksDone` is registered beside `:tasksdone` so both spellings enter browse mode; case-insensitive matching would otherwise make them two candidates for one command, splitting its usage count across two rows. `buildCandidates` drops the variant.
- **`:apps` keeps its substring filter, and that is not an oversight.** A filter and a matcher answer different questions: the browse view's auto-launch fires when the filter narrows to exactly one row, and SUBSEQUENCE alone matches dozens of labels on a real device, so a fuzzy `:apps` would rarely narrow to one.
- **One pause timer, not three** (`ShellScreen`). There used to be one each for aliases, apps and notes, with guards yielding to each other — a hand-written cascade of the kind ADR-0010 exists to delete. The ranking decides *what*; the timer decides only *when*, and it restarts on every keystroke so `alarm` stays reachable with `a` aliased.
- Input containing whitespace with no deterministic hit goes straight to T2 — multi-word input is almost always prose, don't waste a stage on it.
- **Log every resolution** as `(raw_input, resolution)` locally (T014). This is the fine-tuning dataset's real-usage seed — treat it as load-bearing, not telemetry.
- T3 is what makes T2 shippable: the SLM is allowed to fail, the launcher is not.

## Room patterns

- **Outbox from day one** (T018, built). Every mutation to **synced** data — notes, and the checklists derived from them — writes an outbox row in the same transaction as the entity change; that pairing is what makes sync resumable after an interrupted push. Don't add a synced table that can be mutated outside a transaction that also touches the outbox. **Aliases are explicitly excluded** (corrected 2026-08-19): this bullet used to say "notes/checklists/aliases", which predated T097 resolving alias sync as "no". An outbox row for an alias would never drain, because nothing pushes it.
  - `NoteDao` enforces this structurally rather than by convention: the raw insert/tag/enqueue operations are `protected`, so callers can only reach `@Transaction` methods that already do the right thing. `upsertLocal`/`markDeletedLocal` enqueue; `applyRemote` deliberately doesn't (pulled state is already the server's).
  - **The outbox coalesces** — one row per dirty note, keyed by `noteId`, not one per mutation. §4.6's debounced autosave would otherwise queue hundreds of rows pushing identical state. Consequences worth knowing: `enqueue` uses `IGNORE` so `baseRev` stays pinned to when the note *first* went dirty (that's the conflict comparison point, §7.2), and `confirmPushed` only drains the row if the note hasn't changed mid-push.
- **Markdown is the stored format**, per the root constraint — not a rich-text model. Checklist items are `- [ ]` / `- [x]` lines parsed into structured items for the UI, not stored as separate normalized rows (that parser lands with T023/T024). Hashtags (`#work`) are parsed out of the body on save and indexed for querying; the body stays the single source of truth. **Tags live in a `note_tags` join table**, not a delimited column — exact matching, because `LIKE '%work%'` also matches `#workout`.
- **Tag parsing is a cross-language contract, not local logic** (`notes/TagParsing.kt`, T019). Design doc §7.3 has `Notes.Shared` implementing the same rules in C# and names this "the seam where bugs will live", so the rules are pinned in **`fixtures/tag-parsing.json`** at the repo root and executed by both suites. **Change the fixture and both implementations — never one alone.** The repo-root `fixtures/` dir is on the unit-test classpath via a `sourceSets` entry in `app/build.gradle.kts`.
  - `NoteDao.upsertLocal` **derives** tags from the body rather than accepting them, so a caller can't supply a set that disagrees with it. `applyRemote` still takes them, because those are the server's — that asymmetry is deliberate and matters if tag assignment ever moves server-side.
- **One database, `dailydriver.db`** (`data/DailyDriverDatabase.kt`), built once via `DatabaseProvider`. Notes and the outbox *must* share it — a transaction can't span two SQLite files. Never call `Room.databaseBuilder` for it a second time. **`exportSchema` is off, and that's a known gap (T151)** — enabling it on Room 2.8.4 here exports once and then fails every subsequent build with an `AbstractMethodError` in kotlinx-serialization. Solve that before the first real migration; don't just flip the flag.
  - **Notes use `@Upsert`, never `@Insert(onConflict = REPLACE)`.** SQLite implements REPLACE as delete-then-insert, and both `outbox` and `note_tags` CASCADE off `notes` — so a REPLACE on a note silently deletes its pending outbox row. This shipped as a real bug at T018 and was caught only by the instrumented tests. Same trap applies to any future table with children.
- **⚠️ `run-as` does not work on the daily driver, so use `:export`, not the script.** `scripts/export-command-log.sh` reads the database through `run-as`, which requires a **debuggable** build; the phone runs a release build from T159, so it refuses with `package not debuggable`. T166 added `:export`, which writes the log to Downloads from inside the app on any build type. The script stays useful on emulators and debug builds. **Do not make release builds debuggable to work around this** — that exposes app-private data on the device you carry, permanently, to make an occasional maintenance task easier.
  - **Two producers of the same JSONL** (`command/CommandLogExport.kt` and the script), one consumer (T075's hand-labelling). The keys are a contract: change one and change the other. A test pins the key set, and both files point at each other.
  - **MediaStore renames what you give it, in two ways, and both were found by running it.** It reconciles the display name's extension against the MIME type, so `application/json` turns `….jsonl` into `….jsonl.json` — an *unregistered* type like `application/x-ndjson` is what leaves the name alone. And it de-duplicates a repeated name by appending ` (1)` **after** the extension, which a `*.jsonl` glob then skips, so the file name carries a seconds-precision stamp to stay unique on its own. The command reports the location it queries back from MediaStore, never the name it asked for.
- **⚠️ Set `ANDROID_SERIAL` when both a phone and an emulator are connected.** Gradle's `installDebug` picks a device for you, and it picked the phone — which fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE` against the release build and looks exactly like stale package state on the emulator. Several minutes went into rebooting a device that was never the problem.
- **⚠️ Reading the database off-device needs the `-wal` file too.** Room uses WAL mode, so `adb pull`ing `dailydriver.db` alone gives an empty database and `no such table` — on a fresh install the .db is ~4KB while the -wal holds everything. `scripts/export-command-log.sh` copies all three files; use it rather than improvising, and remember this for any future debugging that reads the database directly.
- **Command dispatch has exactly one home** (T178, `command/CommandDispatch.kt`). A command is a token in T140's registry plus a branch in `dispatchCommand`; everything it needs beyond shell state arrives through `CommandEnvironment`, whose only implementation is `MainActivity`. **Don't add a `ShellScreen` parameter to make a command work** — that is how dispatch ended up in the composable, `onSubmit` ended up as eleven no-ops, and the whole surface ended up untestable.
  - `CommandOutcome` says what to record and **whether the prompt clears**. `Stay` is for a browse view with nothing to commit to: clearing `:apps ca` would close the list you are reading and throw away the filter that produced it. That was a regression introduced during T178 and caught by a test.
- **⚠️ Alias definitions are excluded from the T014 log** (`isTrainingExample`). `alias sp = spotify` is configuration, not language anyone will phrase at the prompt — and logging it files it as a **T3 miss**, teaching the set that a working line was unresolvable. T178 dropped this exclusion by accident and only a real export showed it.
- **Anything acting on typed input must log it** (T014). Since T178 there is one place that does: `ShellViewModel.run`, reached by both `onSubmit` and `onResolved`. Before that there were **three** call sites and a fourth path — opening a sole note on the pause — that logged nothing at all: the Enter handler *and* the pause-triggered auto-launch `LaunchedEffect`. T014 originally logged only the first, which silently biased the training set toward inputs typed fast enough to beat the one-second timer. A third such path would need the same treatment.
- **The command log is device-local and never synced** (T014, `command/CommandLogEntry.kt`). It holds every line typed at the home screen, so it has no outbox row and no place in §6.2 — a stronger version of the alias exclusion below. It records the *resolution* (which token, which package), not a §4.3 intent label, because that label space has already gone stale once; mapping happens at §8's hand-labelling step. Misses are logged too, as `T3` rows, since those are the `unknown` examples. Rows deduplicate with a count, which keeps a fine-tune from being dominated by whichever app you open most.
- **Aliases are device-local and not synced** (open item T097, currently resolved as "no"). Don't add an alias sync path without revisiting that decision first.
- Room is authoritative; the network is an optimization. No UI read or write should ever await a network call — that's the desktop client's rule too (design doc §5.4), and Android follows the same shape even though it isn't stated as an explicit constraint there.

## MediaPipe (T2) — GPU backend + LoRA constraints

- **Runtime:** MediaPipe LLM Inference API, pinned at **`com.google.mediapipe:tasks-genai:0.10.35`** (T029). All inference sits behind `slm/InferenceEngine` (T028) so `LiteRtLmEngine` can replace it later without touching the command pipeline — MediaPipe is maintenance-only upstream (§4.4), and the 0.10.35 artifact being five months newer than the guide is what that looks like in practice. **`NoInferenceEngine` is what currently ships**: `MediaPipeEngine` exists but nothing constructs it, and `NoInferenceEngine` is also what runs whenever the model is absent, so "no model" is exercised rather than being an untested null path.
- **⚠ The options live on two objects, and §4.4 said otherwise until T029 corrected it.** `LlmInferenceOptions` carries `modelPath`, `maxTokens`, `maxTopK`, **`supportedLoraRanks`** and `preferredBackend`; `LlmInferenceSessionOptions` carries `temperature`, `topK`, `topP`, `randomSeed` and **`loraPath`**. Applying a LoRA adapter is therefore two steps in two places, which T037's gate has to exercise in full.
- **⚠ `abiFilters` is load-bearing, not housekeeping** (`app/build.gradle.kts`). The native library is ~27 MB *per ABI* and is packaged uncompressed, so release ships arm64-v8a alone (51.2 MB APK, up from 22.0 MB). **Debug must keep x86_64** or the instrumented suite stops installing on the CI emulator with `INSTALL_FAILED_NO_MATCHING_ABIS`, which reads like a broken emulator rather than a build setting. Don't "tidy" the debug list.
- **The model file lives in `getExternalFilesDir(null)`**, not `filesDir` (T029, `slm/ModelLocation.kt`), for the same reason `:export` exists: `run-as` does not work on the daily driver, so app-private storage cannot be reached by `adb push` on a release build. `adb push model.task /sdcard/Android/data/com.flambeauriver.dailydriver/files/model.task`. Presence means *is a file, and non-empty* — an interrupted push leaves zero bytes and a trailing-slash push leaves a directory, and both otherwise reach MediaPipe as an opaque native failure.
- **The structured-output layers are built and tested, ahead of the spike** (`slm/`, T033–T035): `firstJsonObject` → `repairJson` → `parseIntent`. They are pure, need no model, and are required whichever way T037's gate goes, since the few-shot fallback needs them too. **Don't skip a layer to simplify** — each exists because the previous one was measured as insufficient (§4.4).
  - `parseIntent` returns null for *every* failure, including an explicit `unknown` and a below-threshold confidence, because the caller does the same thing in all of them: drop to T3.
  - **Never default a missing `confidence`.** Substituting one manufactures the number the abstention decision rests on.
- **LoRA requires `backend = "gpu"`.** It is not available on CPU backend, applies to attention layers only, and MediaPipe documents it as experimental. Do not attempt LoRA on the CPU backend.
- **Model choice is gated on LoRA support**, not picked upfront, and **it is a four-way choice since T039** (2026-09-22) — see §4.4's table. Short version: **Gemma-2 2B publishes only q8 (2.63 GB) and breaches §2's "< 1.5 GB resident" target**; **Gemma 1.1 2B `gpu-int4` is 1.35 GB, takes LoRA, and fits**, and is the current lean; Gemma-3 1B and 270M fit easily but take no LoRA. T037 is a timeboxed GO/NO-GO spike on the target device before committing — don't build downstream fine-tuning work against a model that hasn't cleared that gate.
- **⚠ You cannot self-convert *and* use LoRA.** MediaPipe's Torch Generative converter is documented **CPU-only**; LoRA inference is **GPU-only**. Any adapter-based path must use a base model Google already converted.
- **⚠ Model loading cannot be tested on an emulator** (T039). The AVD has no OpenCL, so every `createFromOptions` fails at engine init whatever the file. Anything touching T030/T031/T037/T038 needs the S20 FE attached.
- **The old `.bin` format still works** (T039, proven by spike): 0.10.35 parses Kaggle's `gemma-2b-it-gpu-int4.bin` despite the loader being `.task`-bundle-oriented. Don't rule a model out on file extension.
- **⚠ Every official artifact is gated** — `litert-community` `.task` files 401 without a Hugging Face token, and Kaggle's Gemma needs an access request. Community `.bin` re-uploads are open but carry no redistribution standing under T094; fine for a spike, not for T087.
- LoRA adapters are trained with PEFT (`target_modules = ["q_proj","v_proj","k_proj","o_proj"]`) and converted with MediaPipe's `converter.ConversionConfig()`.
- **✨ MediaPipe DOES have grammar-constrained decoding, and this bullet used to say the opposite** ([ADR-0011](../docs/adr/0011-constrained-decoding-and-fine-tuning-as-experiment.md), 2026-09-22). The builder ships in **`com.google.ai.edge.localagents:localagents-fc`**, which depends on `tasks-genai`: `getSentencePieceProcessorHandle()` → `FstConstraintProvider` → `createConstraint(tools, options)` → `getConstraintHandle()` → `setConstraintHandle(...)`. `Schema` has an `enum` list, so §4.3's label space becomes a hard constraint and **the model cannot emit a nineteenth intent**. T190 wires it up.
  - **The five layers below stay, demoted to the fallback path.** Constrained decoding is probably GPU-only (`UpdateConstraintMask not implemented for this backend`, only an OpenCL implementation in the native library), so the layers still run when it is unavailable. **Don't delete a layer because the constraint exists.**
  - **⚠ Structural validity is not correctness.** A constrained `confidence` is still invented by the model. T035's threshold and the `unknown` abstention path are untouched by this.
  - **Fine-tuning is no longer load-bearing for T2**, and LoRA is no longer a hard requirement for model choice (T039). It is benchmarked against a constrained baseline at T083; the winner ships. Schema adherence for the intent/slot JSON output is defended in layers, in order: tight few-shot prompt with the schema inline → low temperature (~0.1) → extract the first balanced `{...}` span → repair pass (trailing commas, unquoted keys, markdown fences) → validate against schema, drop to T3 on failure or low confidence. Don't skip layers to simplify — each one is there because the previous one alone was measured as insufficient.
- Model weights are downloaded at first run (WorkManager, SHA-256 verified, unmetered network only) from Blob Storage — never bundled in the APK. The LoRA adapter (single-digit MB) may be bundled. The launcher must be fully functional at T0/T1/T3 before the model exists on-device.
