# desktop/ — WPF Notes Client

Native Windows app (.NET 10 + WPF, MVVM). Offline-first: SQLite via EF Core is the source of truth, a background `SyncService` reconciles with the backend, and the UI never awaits the network. This is the .NET job-hunt artifact — see root [`../CLAUDE.md`](../CLAUDE.md) for project-wide constraints and [`../docs/design.md`](../docs/design.md) §5 for the full design.

### ✅ Standing exception: unit tests (added 2026-09-14)

**Claude may write and edit test code directly** — `.cs` files under `Notes.Desktop.Tests`, and the test `.csproj` when a test genuinely needs a package or a target-framework change. No need to ask first.

The line is **test code, not testability changes to production code**. Specifically:

- **Allowed:** test classes, `[Fact]`/`[Theory]` methods, fixture/DTO types that exist only to load a corpus, fakes and stubs, test-only helpers, `PackageReference`s the test project needs.
- **Still off-limits:** anything under `Notes.Desktop` itself. That includes changes made *for* a test — widening a member's visibility, adding an `InternalsVisibleTo`, extracting an interface so something can be faked, splitting a class to make it constructible without WPF. Those are design changes with a test as their motivation, and they go through review like any other.
- **When a test can't be written without one of those**, say so and propose the production change rather than making it. "This needs `X` to be `internal` rather than `private`" is exactly the kind of finding this arrangement exists to surface — a hard-to-test class is usually a design smell worth naming out loud, not routing around quietly.
- Tests are still held to everything in **Testing** below: fixtures are the spec, merge/parser logic tested with no WPF or EF Core types, ViewModels tested through public properties and commands rather than the view.

This exception is **`desktop/` only.** [`../backend/CLAUDE.md`](../backend/CLAUDE.md) carries the unmodified rule, so `Notes.Shared.Tests` and any `Notes.Functions` tests remain review-only until that file says otherwise.

If the user explicitly asks for a further carve-out — pairing on one function, a spike to unblock them — that is theirs to grant in the moment; don't assume it from a prior conversation.

**Solution spans folders.** `Notes.Desktop` lives here; `Notes.Shared` (the contract — POCOs, DTOs, parsers) and `Notes.Functions` live in `../backend/`. **T042 landed a real `Notes.Shared` (`net10.0`) and `Notes.Desktop` references it again**, so the cross-folder reference T052 removed is restored and live: `AppDbContext` derives tags and tasks through `TagParser` and `TaskIndex` on every save. Flag any DTO or parsing rule redefined locally to avoid that reference — it is the single source of truth precisely so the two implementations cannot drift. Merge rules are **not** here: they moved to T070 to land with the sync-scenario corpus that gives them an oracle.

Current state: T052–T055 and T057 done. `Notes.Desktop` boots via .NET Generic Host (`App.xaml.cs`), DI-registers the window, the ViewModels, `IRegistryAccess` and `IDbContextFactory<AppDbContext>`, and migrates a SQLite database (EF Core, real `dotnet ef` migrations under `Migrations/`) at startup. The two-pane shell is up: `MainWindowViewModel` is the shell VM holding `NoteListViewModel`/`NoteEditorViewModel`, composed through implicit `DataTemplate`s, with a `GridSplitter` whose position persists to the registry. **The editor pane is real** — `NoteEditorViewModel` loads and saves against SQLite with a 3s debounced autosave, and `Markdig.Wpf` renders live preview into a `FlowDocument` ([ADR-0009](../docs/adr/0009-markdig-wpf-over-webview2.md)). **The note list is still a placeholder** (T056). Tags, tasks and the outbox row are derived in `AppDbContext.SaveChangesAsync(bool, CancellationToken)` — the two-argument override, because the one-argument form delegates to it virtually and is therefore not the chokepoint. ViewModels are CommunityToolkit.Mvvm (`ObservableObject`, source-generated partial properties, `[RelayCommand]`). `Notes.Desktop.Tests` (xUnit v3 + FluentAssertions + Moq, `InternalsVisibleTo`-linked) is at **59 tests**, covering EF Core cascade/constraint behaviour, derive-on-save and outbox coalescing against a real SQLite connection, the registry helper, shell-VM composition/persistence, and the editor VM through its bound properties and commands. Still missing: MSAL, the note list, and sync.

**`IsDirty` is derived, not a flag** (changed 2026-09-21): it compares `Title`/`Body` against the last-persisted snapshot, which `LoadAsync` and `SaveAsync` both refresh. Flag it in review if anything reintroduces a handler that *sets* dirtiness — that shape cannot tell a user keystroke from the editor populating itself, which is how loading a note came to mark it dirty and autosave it. The snapshot holds the ViewModel's CRLF strings, never the LF-normalised persisted ones.

**`LoadAsync` flushes before it loads**, and that belongs in the editor rather than in the shell that calls it. A caller-side flush works until the second caller exists; "loading never loses work" has to be a property of the editor. Same deadline exists at shutdown — `MainWindowViewModel.BeforeShutdown` currently writes the splitter width and does **not** flush the editor, so closing the window within three seconds of typing still loses those characters. Open, and worth fixing with T056.

⚠️ **Three failure modes this client has now hit more than once, all silent at runtime — check for them by reflex:**
- **A bound member that isn't `public`.** T057 shipped `[ObservableProperty] partial string Title { get; set; }` with no access modifier, which is *private*; all three bindings in `NoteEditorView.xaml` resolved to nothing and logged a `BindingExpression path error` instead of throwing. Write `public partial`, and flag a declaration without it on sight.
- **An exception swallowed inside fire-and-forget autosave.** `AutosaveAfterDelayAsync` catches and logs, which is correct, but it means a broken save path presents as "the note stopped saving" with nothing on screen. Anything reached from a debounced autosave needs a test, because the app will not tell you.
- **A disposed `CancellationTokenSource` still referenced by `_debounce`.** Three separate bugs so far, all the same shape: `Cancel()` on a disposed source throws `ObjectDisposedException`, and it surfaces from inside a property setter where nothing expects a throw. The rule that ends it is ownership, not vigilance — **exactly one method may touch `_debounce`**, and everything else calls it. Flag any second writer of that field on sight, including a "quick" inline cancel.

## The schema to mirror

**[`../docs/design.md` §6.2.1](../docs/design.md)** is the canonical spec for the Markdown body syntax — checklist items, due-date tokens, hashtags — and it is pinned by fixture files at the repo root (`fixtures/checklist-parsing.json`, `fixtures/due-date-parsing.json`, `fixtures/tag-parsing.json`) that Android's Kotlin implementation already satisfies in production. **When reviewing a `Notes.Shared` parser, the fixture is the source of truth, not the prose in §6.2.1 and not this file.** A parser that passes its own hand-written tests but disagrees with the fixture is wrong.

Two asymmetries worth holding reviewers to, both easy to "simplify" away incorrectly:

- Tags are *derived* from `body` on every local save (never accepted from a caller) but *trusted* from the server on a pull, since that's already-authoritative state. One code path that ignores the distinction is a bug, not a cleanup.
- **The client's task index stays local, derived and unsynced** ([ADR-0007](../docs/adr/0007-derived-task-index.md), still in force). [ADR-0008](../docs/adr/0008-server-side-task-index.md) gave the *server* its own derived index, which changes nothing on this side: the desktop still derives its own `Tasks` rows from bodies, still never pushes them, and a task-related outbox entry is still wrong. Tasks are a projection on both sides, not a synced entity — flag anything that turns one into one.

## Testing — hold reviewed code to TDD, especially for the sync engine

- **The sync engine is exactly the kind of logic that silently corrupts a user's notes if it's wrong.** In review, a `SyncService`/outbox/conflict-resolution change with no accompanying xUnit test is unfinished, full stop — say so rather than approving it provisionally.
- **The shared fixture corpus is the spec**, for both the body-syntax parsers above and for sync scenarios (`base`/`local`/`remote`/`expected`, §7.3) once that corpus exists. A scenario with no fixture entry doesn't count as covered; disagreement between the C# and Kotlin suites is a failing test to flag, not a judgment call to wave through.
- **xUnit + FluentAssertions**, per the design doc. Merge/conflict logic in `Notes.Shared` should be testable with no WPF or EF Core types involved — flag it in review if a merge-rule test needs a `DbContext` or a `Window` to run.
- ViewModel logic (`CommunityToolkit.Mvvm`) should be tested through public properties/commands, not through the view — no UI automation for anything that isn't a genuine rendering concern.

## Coding style to hold reviewed code to

- **Functional core, imperative shell — for every class, not just the obvious candidates.** All the actual decisions (validation, merge/conflict logic, what a due-date token means, what a save should do) belong in pure functions or pure classes: deterministic, no I/O, no mutable ambient state, trivially unit-testable without a fake anything. Everything that touches the outside world — EF Core, `HttpClient`, the filesystem, WPF's dispatcher — sits in a thin shell that orchestrates calls into the pure core and does nothing else. **This is not a new idea for this project**: `android/`'s `NoteDraft`, `ChecklistParsing`, `DueDateParsing`, and every "pure half beside an impure ViewModel" pattern documented in `android/CLAUDE.md` *is* this split, already proven to make the Android suite worth what it is. Push back in review on a class that mixes a database call with the logic that decides what to write — split it, even if the class is small.
- **Watch for events used as commands, not notifications — this is the specific anti-pattern to flag.** A .NET event should mean "this already happened; zero or more listeners may react however they like," never "please go do this specific thing." Tells that an event has drifted into command-in-disguise:
  - A **name that is an imperative verb** (`RequestSave`, `PleaseClose`, `DoRefresh`) rather than a past-tense fact (`Saved`, `Closed`, `Refreshed`). Flag the name in review even before looking at the usage — it's usually a reliable signal.
  - **Exactly one subscriber is expected to exist**, and the code silently depends on that subscriber's specific side effect happening synchronously (or "soon enough") — that's a direct call wearing an event's clothes, and multicast semantics only add risk (a second handler added later, a missing handler silently doing nothing) with no benefit.
  - A ViewModel raising an event so the **View** does something specific (close a window, focus a control, show a dialog) — WPF has real mechanisms for this (a bound `ICommand`, a behavior, an interaction request/messenger pattern with a properly-named message) that don't rely on an ad hoc single-purpose event.
  - **The fix is almost always a direct method call or an injected interface**, not a better-named event. Reserve actual events for genuine one-to-many fan-out where the publisher truly does not know or care who's listening. `ICommand` (a WPF/MVVM command object bound to a button) is a different, legitimate thing — don't conflate "flag event misuse" with "flag `ICommand` usage."
- **Be harsh reviewing MVVM boundary violations — this is a review posture, not just a checklist.** "It works" is not a defense, and a boundary crossed once quietly becomes a habit by the third occurrence. Don't soften a finding because the violation is small, the fix is inconvenient, or it's easier to let one instance slide — name it plainly and require the fix before approving. Concretely, flag:
  - **A ViewModel referencing any WPF/PresentationFramework type** — `Window`, `FrameworkElement`, `Control`, `Brush`, `Dispatcher`, anything from `System.Windows.*` beyond what `CommunityToolkit.Mvvm`'s source generators already produce. A ViewModel that needs the WPF runtime to construct or test has already crossed the line; the entire point of the toolkit's generated observables is to keep the ViewModel POCO-shaped and testable without a `Window`.
  - **Code-behind (`.xaml.cs`) doing anything beyond `InitializeComponent()` and genuine view-only concerns** — focus management, an animation trigger, drag-and-drop plumbing. A click handler that touches `DbContext`, calls a service, or makes a decision is business logic wearing a UI event's clothes; it belongs in a `[RelayCommand]` on the ViewModel.
  - **The View reaching past the ViewModel** — direct `DbContext` access, a direct `HttpClient` call, or a service resolved and invoked from code-behind instead of through the bound ViewModel. The View's only contract is the ViewModel's public surface; nothing else is a legitimate shortcut.
  - **Business or domain logic living inside a `[RelayCommand]` handler instead of `Notes.Shared`.** This is the functional-core/imperative-shell rule above, applied specifically at the ViewModel/Model seam — a command handler should read as *call into the pure core, assign the result to an observable property*, not decide the outcome itself.
  - **A `Notes.Shared` POCO carrying WPF-facing concerns** — `INotifyPropertyChanged` added purely for binding convenience, an `ICommand` property, a validation message phrased for display rather than for a caller. A domain entity describes data; presentation concerns belong one layer up, in the ViewModel.
  - **Manual `PropertyChanged` subscriptions in code-behind that react with logic**, in place of binding or a behavior. This is the event-misuse rule above, applied at exactly the View/ViewModel seam it's most likely to appear at — a ViewModel announcing that something changed must never be read by the View as an instruction for what to do next.

## Simplicity

- **This is a single-user, single-tenant app.** Push back on abstractions (repository-over-repository, generic CRUD frameworks, plugin systems) that only pay off with multiple consumers or implementations. EF Core's `DbContext` is the repository.
- **Three projects, not more.** `Notes.Shared` / `Notes.Desktop` / `Notes.Functions` is the whole structure (design doc §5.2). Flag a proposal to split further for "separation of concerns" — at this size that's overhead, not architecture.
- **No premature sync generality.** The conflict policy is last-write-wins-on-`rev` with a conflict copy — deliberately not a CRDT (design doc §7.4). Flag anything building toward one "in case requirements grow."
- Prefer the terse, idiomatic C# construct (expression-bodied members, pattern matching, `is null`) over a verbose equivalent, but not at the cost of readability in the sync/conflict code — that code gets read under pressure when something's gone wrong, and terseness that costs a beat of comprehension there isn't a good trade.

## Conventions to hold reviewed code to

- **MVVM via `CommunityToolkit.Mvvm`.** Source-generated `[ObservableProperty]`/`[RelayCommand]` — flag hand-rolled `INotifyPropertyChanged`.
- **Views composed by implicit `DataTemplate`, and therefore parameterless (T055).** A child View is reached by binding a `ContentControl` to a ViewModel and letting a `DataType`-keyed `DataTemplate` resolve it; the template sets that View's `DataContext` itself. So flag two things in review: a `UserControl` constructor taking its ViewModel (WPF's BAML loader instantiates template content, **not** the DI container — a required parameter cannot be satisfied and the View simply fails to construct), and a `DataContext = …` assignment in a child View's code-behind (it overwrites what the template already set correctly). `MainWindow` is the one exception, resolved from the container at the composition root because nothing templates it.
- **Binding only sees `public` members.** WPF's binding engine never reflects over non-public members, so an `internal` `[ObservableProperty]` or `[RelayCommand]` binds to nothing — and fails *silently*, logging `BindingExpression path error` to the debug output rather than throwing. Both of this project's binding bugs so far were this or a property-name typo, and neither surfaced as an error. Flag non-public bound members on sight.
- **The UI never awaits the network.** All reads/writes go through EF Core; `SyncService` (an `IHostedService`) reconciles in the background on a timer, on reconnect, and on demand. A ViewModel calling an `HttpClient` directly is a bug to flag, not a style nit.
- **Outbox in the same transaction as the entity change.** This is what makes an interrupted sync resumable — flag an outbox write proposed as a separate step that could fail independently of the entity write.
- **`HttpClient` via `IHttpClientFactory` + Polly** for retry/backoff — the network is assumed flaky, not exceptional.
- **Auth is MSAL.NET, public client, PKCE, no client secret.** A desktop binary can't keep a secret; flag one if it appears.
- **Markdig** for Markdown rendering/round-trip — matches the storage format from the root constraint. Checklist checkboxes rewrite the underlying `- [ ]` / `- [x]` line per §6.2.1's parser; there is no separate checklist-item table.
- **Light + dark, bound to system preference.** This is the one client with both themes (design doc §5.3) — deliberate asymmetry with Android's dark-only.
